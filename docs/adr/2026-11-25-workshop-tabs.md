# ADR 2026-11-25 — Independent Workshop tabs

**Status** Accepted for the Workshop tabs epic in [PR #301](https://github.com/okeylanders/prose-minion-vscode/pull/301). T1 requires multiple unsaved rooms. Revised after [PR 301’s design review](../pr-reviews/pr-301-workshop-tabs-design-review-6b8d0e76.md).

**Scope** Each VS Code Workshop tab can hold its own room, run and recoverable manuscript discussion. The Lightbox continues to hand material to Workshop through its existing commands. [Epic and sprint gates](../../.todo/epics/epic-workshop-tabs-2026-11-25/README.md) · [Feature 9 and T1](../../.todo/features/feature-multiple-workshop-and-lightbox-tabs/README.md)

## Ownership at a glance

| Lifetime | Responsibilities |
|---|---|
| Extension window | Panel and room registry, recent Workshop focus, named-session ownership, shared workspace stores and their write coordination, provider resources, user settings. |
| Durable room slot | Rolling checkpoint location, workspace identity, association with the panel's restore state. The same slot can host a different session after New or Open. |
| Loaded room | Session aggregate, retained conversation bindings, projected settings and time, persistence coordinator, replacement revision, recall's open-room reader, run cancellation and deferred operations. |
| Attached panel | Webview, message handler with its own reply function, visibility, subscriptions and seed delivery. A new webview attachment has a new receiver. |

Today the path is panel → handler → shared room. Each panel already supplies its own reply function in [WorkshopPanelProvider.attachPanel](../../apps/vscode-extension/src/application/providers/WorkshopPanelProvider.ts). The single session is captured during [activation](../../apps/vscode-extension/src/extension.ts) by delivery, settings, persistence, transcript recall, capability execution, project memory provenance and export. A reply routed back to the correct tab can therefore still report a mutation of the wrong room.

### D1. Bind the destination when attaching the panel

The composition root provides a room factory and window registry. Attach the handler to a particular slot's services and that panel's reply function once. Incoming messages cannot select a different room. Shared commands that start outside a panel choose their destination at the gesture and keep it through awaits. Window-wide services may continue publishing truly global events such as account balance changes. Retain real room-replacement checks within a slot, including the [existing asynchronous context-read case](../../.todo/tech-debt/2026-11-18-workshop-room-context-reads-unbound-to-room.md).

The registry chooses where to open or reveal a room. It never reassigns in-flight replies by looking at focus. Adding a return-tab field to every message duplicates the trusted destination supplied by the adapter. An outbound-only proxy cannot isolate the session aggregate, persistence, or listeners. The room factory keeps those choices at the composition boundary.

### D2. Capture room dependencies together

Each room owns an independent coordinator, operation queue, active run and its asynchronous work. Each settings reader or callback whose result depends on the live session binds to that room. This includes the assistant prompt grammar callbacks registered in activation, conversation-history export/import, session timezone, recall bookmarks, persona tools and Passage Search's pending approval and result delivery. Shared providers and file-backed libraries can serve multiple rooms through room-scoped callers. A saved-session operation initiated in A must respect any active owner of its target in B. Named revisions and the store's compare-and-swap still protect writes from separate windows.

**Witness.** A starts a delayed turn or file read. The writer focuses B and starts or cancels work there. A's completion updates A, B keeps its own history, and a replacement or close of A invalidates A's stale work. Rewind uses its existing revision rules. [Room replacement contract](../../packages/core/src/application/services/workshop/WorkshopOpenRoomInstance.ts) · [Workshop teardown order](../../packages/core/src/application/handlers/domain/workshop/WorkshopSliceComposition.ts)

### D3. Give every scratch room a durable address

Reserve the host slot id `legacy` for the existing `current.json` so an upgrade and an old serialized panel can reopen genuine writer data through the existing decoder. Other slots get host-generated UUIDs with private rolling checkpoint locations. Use a dedicated scratch storage namespace or explicitly exclude rolling files and their sidecars from named-session scans. Keep the persisted conversation format and existing recovery/atomic-write rules. Validate serialized slot identifiers before resolving them to host-controlled paths. A malformed or duplicate restore cannot take possession of another panel's scratch checkpoint.

VS Code restores the panel's slot identity. In a single-folder workspace the host reads its authoritative checkpoint from disk. **Reopen Closed Workshop Room…** lists closed slots. The picker also lists rooms retained by the host after a failed write, including a first write that left no file to list. [Store availability and session listing](../../packages/core/src/infrastructure/storage/WorkshopSessionStore.ts) · [Session codec compatibility](2026-07-30-workshop-session-codec-evolution.md)

**D3a · Close has a durability outcome.** Detach the panel, stop its producers, invalidate old reads and mark the slot closing. The registry keeps its room, histories and ownership claims until the coordinator joins prior session operations, autosave work and named-to-rolling mirrors. Judge success from committed revisions, outstanding mirrors and any protected dirty checkpoint. A settled promise alone does not establish durability. Reopen during close joins the close in progress before it attaches a handler. Successful close may release disk-backed state. A failed close keeps the writer's newest room in memory, reports the failure and retains its claims. The picker can reattach that room for another save attempt. A previously readable checkpoint survives failure. Shutdown starts each room's close and awaits all room and shared-store drains before reporting a failure. [Persistence coordinator](../../packages/core/src/application/services/workshop/WorkshopSessionPersistenceCoordinator.ts) · [Extension shutdown](../../apps/vscode-extension/src/application/extensionShutdown.ts)

**D3b · A room can live in memory.** With no workspace folder or several workspace roots, Workshop has no single project session store. Keep each closed room in its host registry, including its history, until it is reopened or that extension host exits. The same picker can reopen either room independently. State recovery across a host restart requires a single-folder workspace with a committed checkpoint. Opening and closing a tab cannot choose an arbitrary workspace root. [Store availability](../../packages/core/src/infrastructure/storage/WorkshopSessionStore.ts)

**D3c · Protect rolling checkpoints across extension windows.** Two independent hosts may open the same project, select the same closed UUID slot, or both restore `legacy`. Each store remembers the exact rolling bytes it accepted (or that the file was absent). Every rolling create, replacement or sidecar publication takes the slot's on-disk claim, checks the accepted bytes or absence again under that claim, and publishes only while it owns the claim. The guarded replacement advances the store's expected checkpoint only after commit. Corrupt or unreadable bytes are a protected checkpoint. They cannot become an expected absence. Busy claims can be retried. A stalled claim cannot be taken over solely because time passed. [Claim and recovery precedent](2026-11-19-workshop-persona-tools.md)

If the check finds another writer's committed version, preserve that winner's rolling file. Fork the loser's *latest local state* to a separately named local recovery session, created without overwrite. Later local updates use the recovery session's own checked revision. Inform the writer which copy holds their edits. Preserve the losing in-memory room and protect the disputed slot until recovery has a known outcome. A retry after an interrupted recovery cannot replace a different saved session or destroy the only local copy. This rule applies to the rolling mirror of a named session as well as an unnamed scratch write. The named file's own compare-and-swap continues to apply. [Named storage and recovery contracts](../../packages/core/src/infrastructure/storage/WorkshopSessionStore.ts)

### D4. One open writer per named session per window

Use workspace and durable named-session id for ownership; tab titles and paths can change. Reserve the destination before an asynchronous open, so simultaneous opens converge on one owner. A second open reveals that owner. Retain the original ownership until a replacement commits. Release a provisional claim on failure and preserve the original room. Serialize or coordinate restore, promotion to named, reload, rename, branch, and writes from the saved-session to-do tool at the same boundary. A tab closing a named session holds its claim through its final flush. A dirty rolling copy displaced by an authoritative named checkpoint follows the coordinator's existing recovery-copy rule before adoption. Two tabs restoring the same named checkpoint must converge without overwriting either scratch copy. [Persistence coordinator](../../packages/core/src/application/services/workshop/WorkshopSessionPersistenceCoordinator.ts) · [Rewind and Branch](2026-09-30-workshop-rewind-and-branch.md)

### D5. Give external commands predictable targets

Open Workshop reveals the primary room or opens it when its tab is closed. New Workshop Tab opens the primary room when no Workshop tabs are open and creates a fresh independent room whenever any Workshop tab is open. Send Selection, excerpt seeding and Lightbox handoffs choose the most recently focused Workshop panel when invoked, or open one if necessary. A mount, a reveal or a restored hidden panel cannot steal a delivery already offered to another panel. Tab titles distinguish concurrent rooms, including unnamed ones. Keep the existing Branch command's destination behavior. A separate Branch into New Tab command can be considered after ordinary independent tabs work.

**D5a · Capture the Lightbox destination and the receipt together.** At the writer's gesture, before a file reread or other await, capture the intended Workshop slot and the loaded room's generation. If no Workshop is open, reserve the destination to open once the source check succeeds. A change of focus may update the visible tray, but cannot redirect the send. When a staging acknowledgement is lost, verify the tile's board/tile identity against the original room generation or that delivery’s committed receipt. Resetting A cannot let a later A or an identical tile in B answer for the old room. If A closed, report staged only when evidence from the original room/delivery confirms it. Lightbox shows the tray for the most recently focused open Workshop, clears the tray when no owner remains, and its Open Workshop action reveals the room represented by the displayed tray. [Lightbox handoff and lost acknowledgement](../../packages/core/src/application/handlers/domain/LightboxHandoffRoute.ts)

**D5b · Attribute usage at the boundary that knows it.** The token widget’s cumulative usage and last completed request cost are global to this extension window. Label both scopes explicitly. All attached views receive the same totals and latest price; a newly attached view initializes from the window's current snapshot. Global reset applies across views. The price can be unknown. Each Workshop turn separately keeps its own completion usage and displays its reply and usage only in the initiating room. Carry that result along the run’s existing completion callback and room-bound delivery. The global usage stream carries no evidence of which room originated a turn. [Usage multicast](../../packages/core/src/infrastructure/api/orchestration/AIResourceManager.ts) · [Turn completion](../../packages/core/src/application/services/workshop/WorkshopRunCompletion.ts)

## Review and release witnesses

- Start two unsaved rooms with distinguishable excerpts and turns. Pin, rewind, abort and export in A; check B's history, pins, export, and active run.
- Hold a read, switch tabs, replace the initiating room, then resolve the read. Inspect both ledgers, including the durable checkpoint after reload.
- Open the same named session through two tabs concurrently, then exercise a rejected open and retry. One named owner and a recoverable originating room survive each outcome.
- Reload with both tabs present, including an old panel state and a pre-feature `current.json` fixture. Close, reopen and shut down with pending writes. One failing flush must still let every other flush settle.
- Two independent windows, each with its own registry/store over the same workspace, restore the legacy slot, then race writes with distinct text. Repeat for a UUID slot opened from both pickers and for two creates from an absent checkpoint. The committed rolling file and the recoverable fork account for both inputs. A recovery retry leaves the previously committed text intact.
- Hold a real session operation across close/reopen and keep failing the real scratch store's write. The previous file remains readable, the other room drains, and the retained slot retries its latest edit successfully after writes resume.
- With no folder and with two roots, open two distinct rooms, close both and reopen both in the same host. Neither creates a project session file. Restart expectations follow D3b.
- Start a Lightbox handoff to A, hold the source reread, focus B and put the same tile in B. Lose the acknowledgement with A still open, A reset, and A closed. Only the original result decides success. The visible tray and its Open action identify the same room.
- Start synthetic differently priced runs in A and B, complete B then A, and open a third view. Each turn receives its original usage and delivery. All global views report both completions and the latest cost, including the late subscriber.
- Exercise the installed extension's menu commands and help entry. Sprints record the smoke actions actually exercised and distinguish fixture checks from real Extension Development Host runs.
