### F1 · P2 · A read can still commit after its panel closes

[WorkshopContextHandler.ts:235–253](https://github.com/okeylanders/prose-minion-vscode/blob/911274c98048e77d786123beb44cb186999ee33f/packages/core/src/application/handlers/domain/workshop/WorkshopContextHandler.ts#L235-L253) captures the aggregate revision, but [dispose():208–217](https://github.com/okeylanders/prose-minion-vscode/blob/911274c98048e77d786123beb44cb186999ee33f/packages/core/src/application/handlers/domain/workshop/WorkshopContextHandler.ts#L208-L217) only aborts the wizard. Closing the panel disposes its handler, not the window-owned session (`WorkshopPanelProvider.ts:235–248`; `extension.ts:313`). The slice then starts its persistence flush (`WorkshopSliceComposition.ts:545–561`). A slow file or catalog read returning after that point sees the **same** revision, stages the item and marks the session dirty via the disposed handler. Reopening the same room can show an attachment added after close; the final close flush also cannot cover work that did not exist when it finished. Focus/visibility changes alone should not invalidate an operation.

**Fix and witness:** Give these reads an attachment-lifetime token (or disposed flag) independent of the room revision. Invalidate it synchronously before flushing and check it before subsequent reads, mutations, notifications and dirty marks. Hold a synthetic read, dispose the originating handler without resetting the session, then release it. Assert no attachment, no post-dispose message or dirty mark, including after another handler attaches to the same aggregate. Keep a separate control in which the panel is hidden but not disposed and the read still lands.

### F2 · P2 · A replaced room’s file can block the new room’s send

[WorkshopContextHandler.ts:561–581](https://github.com/okeylanders/prose-minion-vscode/blob/911274c98048e77d786123beb44cb186999ee33f/packages/core/src/application/handlers/domain/workshop/WorkshopContextHandler.ts#L561-L581) binds the *staging* of a message attachment to its room, but not its membership in the send barrier. [WorkshopMessageAttachmentReads.ts:40–72](https://github.com/okeylanders/prose-minion-vscode/blob/911274c98048e77d786123beb44cb186999ee33f/packages/core/src/application/handlers/domain/workshop/WorkshopMessageAttachmentReads.ts#L40-L72) keeps one set per handler. New/Open can replace A with B while keeping that handler. A fresh message sent **in B**, before A’s outstanding read settles, waits on A’s promise. When A’s correctly withdrawn read returns a refusal, B’s otherwise valid send is rejected; if the read stalls, B waits up to ten seconds before refusal. B did not pick that file. The existing test titled “a room replaced during the read” sends B’s message only *after* A’s read settles (`WorkshopSendAwaitsPickedAttachment.test.ts:176–197`), so it cannot distinguish the two cases.

**Fix and witness:** Scope `track`, `pending` and `settle` by the initiating room revision; preserve the refusal for a send actually started in A. In the composed-route test, hold A’s read, replace A, send B’s first message while A’s read is still pending, and verify B’s mock model call runs immediately with B’s input only. Release A; no stale file, refusal or draft restoration should be attributed to B’s send. Also check the adjacent message-catalog path at `WorkshopContextHandler.ts:595–609`: if catalog creation fails after replacement it currently reports the old provider’s error, and if it succeeds it starts loading the first file before noticing the revision change. Recheck on both outcomes as the standing-context route now does.
