# PR #307 · Workshop launcher review

**Request changes.** Reviewed `dc9a739e80cc6f2415c692b1e562d18130ec3552` against `epic/workshop-tabs` at `6a720dc81b361f55e102fe923166214da7bd7af8`. Ordinary **Workshop** and **+** now do the right thing, including when the existing primary editor has not yet been handed to the extension. Two paths still break when an editor is being restored.

### P2 · Sending an excerpt can reassign the original primary tab to a blank room

After reload, a writer can be looking at a manuscript while their primary Workshop is already in the tab bar but not yet attached. **Send to New Workshop Excerpt** asks [the targeting helper](https://github.com/okeylanders/prose-minion-vscode/blob/dc9a739e80cc6f2415c692b1e562d18130ec3552/apps/vscode-extension/src/application/providers/WorkshopPanelProvider.ts#L203-L209) for a destination. Unlike Home, this helper treats an empty focus list as permission to create a new primary. When the original editor eventually supplies its valid saved slot, [the collision rule](https://github.com/okeylanders/prose-minion-vscode/blob/dc9a739e80cc6f2415c692b1e562d18130ec3552/apps/vscode-extension/src/application/providers/WorkshopPanelProvider.ts#L225-L232) assigns it a fresh UUID. The old native tab no longer shows its old room. The primary checkpoint is not shown to be lost; it now belongs to the newly created tab.

Two independent provider checks observed one extra native editor and acquisitions of `legacy`, then a fresh UUID: once with the excerpt command alone, once after Home selected the original editor but before its serializer finished. The no-target helper predates this PR; the new lazy-restore guard protects the launcher but not callers racing it. [Selected Text and tokenless tray navigation](https://github.com/okeylanders/prose-minion-vscode/blob/dc9a739e80cc6f2415c692b1e562d18130ec3552/apps/vscode-extension/src/application/providers/WorkshopPanelProvider.ts#L144-L162) use the same helper. [Lightbox's no-recipient fallback](https://github.com/okeylanders/prose-minion-vscode/blob/dc9a739e80cc6f2415c692b1e562d18130ec3552/apps/vscode-extension/src/application/providers/WorkshopPanelProvider.ts#L164-L185) also creates primary directly; these are code traces, not additional failing witnesses.

**Fix gate:** separate obtaining a primary attachment from bringing it to the front. A caller needing a primary must join or reserve restoration of the actual native editor. Preserve the recipient selected at the gesture; don't look up whichever room happens to be focused after the wait. If no target is knowable, decline rather than reassign an existing slot. Keep the normal, already-attached MRU path intact.

### P2 · An earlier Home click overrides a later + click

Home may wait for a lazily restored primary's serializer. While it waits, **+** correctly opens and focuses a fresh secondary. When the old request resumes, [restorePrimary calls revealRoom unconditionally](https://github.com/okeylanders/prose-minion-vscode/blob/dc9a739e80cc6f2415c692b1e562d18130ec3552/apps/vscode-extension/src/application/providers/WorkshopPanelProvider.ts#L74-L98). In a held-serializer check, both the foreground native tab **and the target captured for the next Lightbox handoff** switched from the fresh secondary back to primary, with no further writer gesture. This affects the next target selection; it did not redirect an offer already captured for the secondary.

**Fix gate:** invalidate the older navigation request when the writer chooses a newer destination. It can still finish attaching the primary in the background, but must not focus it, change the MRU destination, or continue cycling editor groups on behalf of the superseded request. Assert the active native editor and the next handoff target after Home → + → delayed serializer.
