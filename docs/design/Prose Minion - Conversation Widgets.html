Widgets — a third kind of thing in the room

Tools run once and return an artifact. Messages just say things. A widget is played before it commits: it opens from a new Widgets button beside Tools, the writer plays inside a pre-commit surface, and the commit drops two things into the thread at once — a visible event and an optional shaping payload on the rail its lifetime selects (one-shot → thread-artifact; durable → standing prose directive).

It's interactive: §1 runs the whole spine using Sprint 01's widget as the stand-in — click Widgets, play, commit, then re-open the chip. Each widget's own decisions now live on its own spread; this page is the host, the browser, and the rails. Gesture Playground → Spread 01.

What this frame decides
  • Widgets sits beside Tools — the composer's third affordance: + attaches, Tools runs one-shot analyzers, Widgets opens play-before-commit surfaces. Coral tint marks it as a PM-native, stateful door.
  • Nothing lands until commit. The modal edits a local Draft; Cancel/Esc discards it. Only a commit adds the selected artifact to the room.
  • Persona protocol, minimum viable — Jill's message carries a recommend chip with an optional prefill seed. Launch falls out of recommend; auto-commit is out of scope in Sprint 01.
  • The commit is a normal turn — a visible message plus a one-shot thread-artifact that rides exactly one turn, then becomes ordinary history.
  • Clone-and-recommit. The chip on a committed turn re-opens the exact prior Draft; committing again creates a new turn at the head. The old chip stays as a historical marker — history is never rewritten.
  • The widget in this demo is a stand-in for the pattern. Gesture Playground's own input shape, menu grouping, and committed frame are on Spread 01.

Anatomy & decisions
  • Rail badge per widget — lifetime is the load-bearing choice, so it's on every row: one-shot (coral) rides one turn as a thread-artifact; standing (amber) installs a passage-scoped prose directive; resource (blue) keeps durable truth outside the thread.
  • Honest registry state — only Sprint 01 is clickable. Committed sprints and concept springs are visible but disabled, so the menu is a roadmap, not a lie.
  • Full blurbs, never truncated — same conviction as the Model Browser: this surface beats a flat menu because it can explain.
  • The Dictionary is in the registry now — as a report widget, not the participant-with-a-popup it looked like from here. Its run is its commit, and the whole report rides one turn: Spread 10.
03

Two rails, and one spread per widget

where a commit can land, and where each widget's decisions are drawn

The railslifetime is the load-bearing choice
a widget picks exactly one at commit
one-shot → <thread-artifact> rides exactly one turn, then becomes ordinary history. re-launch semantics: clone-and-recommit. standing → <prose-directive> re-shipped each run while active, consulted only when prose is written; one per family, killable in one click. re-launch semantics: edit-in-place + shift marker. resource → project file durable truth outside the thread; the commit leaves a visible event, the knowledge lives in the project.

Everything else — the composer button, the browser, the Draft persistence, the neutralizer registration — is shared host machinery. A new widget should only have to bring its pre-commit surface and the frame it commits.

Each spread follows the same shape: the rail live in §1, the pre-commit surface, then what actually commits. Concept springs use the template too — that's how a spring gets argued with before it becomes a sprint.

Why one page per widget
  • The system page stops growing. This spread argues the host, the browser, and the rails; it doesn't have to re-litigate every widget's inputs.
  • Widgets get compared like for like — same three sections, same order, so the differences that matter (lifetime, surface, committed frame) sit in the same place on every page.
  • A concept spring is cheap to draw and cheap to kill. One page, one template, no edits to the system spread.
